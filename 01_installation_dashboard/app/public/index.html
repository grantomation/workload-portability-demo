Demo Order

Sequential steps for running the live demo. Press each button when ready.

1

Create Disaster Recovery Pairs

Creates DRPs between all Portworx clusters in display order, forming a chain. Uses the configured S3 bucket for async replication.

Ensure your cluster order is correct before creating DRPs. The chain follows the display order of Portworx-role clusters.
2

Create Protection Group

Create a PG for a specific hop right before you demo it. This triggers an immediate initial sync.

3

Prepare On-Prem

Deletes the portable-workload namespace on the last cluster in the chain before migrating back. This avoids resource conflicts when the DR failover lands.

4

Deep Clean

Scans the hub for DRPs, PGs and DR Actions, then walks every Portworx-role cluster checking portworx and kube-system namespaces for stork artifacts (BackupLocations, ClusterPairs, MigrationSchedules, Migrations, DR secrets) plus cluster-scoped SchedulePolicies. Anything that doesn't match a live DRP/PG UID on the hub is an orphan — typically left behind by the multicluster agent or from manual console deletions.

MTV Migration Guide

Overview

After MTV is installed and providers are ready, replace <source-provider-name> with the name you configured in MTV, then create the mapping and plan resources below in the openshift-mtv namespace. These cannot be fully automated as they depend on your legacy virtualization environment.

1. Create a NetworkMap

Maps the source legacy virtualization network segment to the target cluster networking. Use pod networking unless you have Multus/SR-IOV configured.

networkmap.yaml 
apiVersion: forklift.konveyor.io/v1beta1
kind: NetworkMap
metadata:
  name: legacy-to-pod
  namespace: openshift-mtv
spec:
  provider:
    source:
      name: <source-provider-name>
      namespace: openshift-mtv
    destination:
      name: host
      namespace: openshift-mtv
  map:
    - source:
        name: <source-network-segment>
      destination:
        type: pod

2. Create a StorageMap

Maps the source legacy virtualization datastore to the target StorageClass. Use px-csi-replicated for Portworx or the default StorageClass for your cluster.

storagemap.yaml 
apiVersion: forklift.konveyor.io/v1beta1
kind: StorageMap
metadata:
  name: legacy-to-portworx
  namespace: openshift-mtv
spec:
  provider:
    source:
      name: <source-provider-name>
      namespace: openshift-mtv
    destination:
      name: host
      namespace: openshift-mtv
  map:
    - source:
        name: <source-datastore>
      destination:
        storageClass: px-csi-replicated

3. Create a Migration Plan

References the providers, maps, and source VMs. The target namespace portable-workload is pre-created when MTV is assigned.

Important: Set skipGuestConversion: true — guest conversion is not needed for these VMs and will cause failures if enabled.
plan.yaml 
apiVersion: forklift.konveyor.io/v1beta1
kind: Plan
metadata:
  name: legacy-to-ocp
  namespace: openshift-mtv
spec:
  type: cold
  warm: false
  targetNamespace: portable-workload
  skipGuestConversion: true
  preserveStaticIPs: false
  provider:
    source:
      name: <source-provider-name>
      namespace: openshift-mtv
    destination:
      name: host
      namespace: openshift-mtv
  map:
    network:
      name: legacy-to-pod
      namespace: openshift-mtv
    storage:
      name: legacy-to-portworx
      namespace: openshift-mtv
  vms:
    - name: <source-vm-name>
    - name: <source-vm-name-2>

4. Start the Migration

Start from the MTV UI (Forklift plugin in the OpenShift console) or create a Migration CR:

migration.yaml 
apiVersion: forklift.konveyor.io/v1beta1
kind: Migration
metadata:
  name: legacy-to-ocp-run
  namespace: openshift-mtv
spec:
  plan:
    name: legacy-to-ocp
    namespace: openshift-mtv

Pre-created Resources

The following are automatically created when the MTV role is assigned:

  • portable-workload namespace (migration target)
  • Forklift controller RBAC in target namespace
  • Privileged SCC for forklift-controller
  • Cross-namespace image pull access
  • KubeVirt admin role for console VM management
  • Configure the source provider separately in MTV after installation
  • OpenShift providers for clusters with the virt role
