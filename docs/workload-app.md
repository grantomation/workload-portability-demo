# Workload application

The application is a Node.js frontend and PostgreSQL backend, installed natively
inside two Alpine VMs. Its map records a sequence of stops as the workload moves
between environments. Stops persist in the backend's database on its VM disk.

## Platform identification

`02_workload/portable-infra-detect.sh` writes JSON to `/run/portable-infra`. The
server reads that file and exposes it at `/api/infra`. It retries reading while
detection is pending and caches a completed result.

The detector checks for KVM using `virt-what`. KVM guests query cluster metadata;
other results, including a missing or failed detection command, use `Legacy Infra`.
That fallback is a generic label, not proof of a particular source platform.
Metadata requests have bounded retries and can yield `Unknown`. `K8S_API` overrides
the detector's metadata endpoint; `INFRA_OUTPUT_FILE` overrides its output path
when invoking the script. The application itself reads the default path above.

New stops store the detected platform label in the existing database column named
`url`. That name is retained for schema compatibility: it no longer means a route
captured from the request. Older database rows may still contain route URLs.

## Server and database

The server listens on port 8080 by default and connects to PostgreSQL in the
background. Initial connection attempts cycle through `pw-backend-svc` and
`pw-backend-svc.local`, retrying every two seconds. `DB_HOST` selects a single
alternative hostname. OpenShift uses Service DNS; the legacy network uses mDNS.
The client polls health to recover from temporary database unavailability.

`/health` returns HTTP 200 with `database: connected` only when a database query
succeeds. It returns HTTP 503 while connecting or when the query fails. A running
HTTP server therefore does not imply the database is ready.

| Endpoint | Purpose |
|----------|---------|
| `GET /api/infra` | Detected platform and detection source |
| `GET /health` | Database readiness |
| `GET /api/stops` | Stops in ID order |
| `POST /api/stops` | Add `{name, x, y}` and the current platform label |
| `DELETE /api/stops/:id` | Delete a stop |
| `GET /db` | Debug listing of stored rows |

The `stops` table contains `id`, `name`, `x`, `y`, `color`, `url`, and `created_at`.
IDs are generated by a sequence; colors are chosen from an eight-color palette
using that ID. Coordinates are percentages, clamped to x=2–98 and y=4–95.

## User interface

The browser uses vanilla JavaScript and a deterministic procedural terrain map.
Double-click to add a stop, select a pin to inspect the journey, drag to pan, and
scroll to zoom. The UI supports light and dark themes. Its distance and uptime
counters describe the displayed journey; they are not service-availability metrics.

`public/standalone.html` is a self-contained design preview with mock data.

## Local preview

From the repository root:

```sh
cd 02_workload
npm ci
node server.js --dev
```

Open `http://localhost:8080`. Development mode uses example stops and an in-memory
store, with no PostgreSQL dependency. Changes disappear when the process exits.
Run without `--dev` to use PostgreSQL.

| Variable | Default | Purpose |
|----------|---------|---------|
| `PORT` | `8080` | HTTP port |
| `DB_HOST` | Both service-name candidates above | Override database hostname |
| `DB_PORT` | `5432` | Database port |
| `DB_USER` | `todo` | Database user |
| `DB_PASSWORD` | `todo` | Database password |
| `DB_NAME` | `todo` | Database name |
| `DB_SSL` | Unset | `true` enables TLS with certificate verification disabled |

The default database and VM passwords are demo defaults. Changing the runtime
password also requires matching database configuration; do not bake environment
secrets into images intended for distribution.
